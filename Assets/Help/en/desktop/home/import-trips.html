Import a broker's trips

How to load a broker's CSV, what the screen checks before sending anything, and how to put right the trips that do not go in without leaving it.

how-toNew in 1.6.1

Importing puts the trips a broker sent you in a file into the system, without typing any of them by hand.

When you need it#

The broker has sent tomorrow's CSV and those trips have to be on the Home tab before anybody starts routing.

At a glance#

Top right, the screen always says where you are: 1 Choose → 2 Import → 3 Review. Nothing is sent until you ask for it, and nothing is lost by getting it wrong: importing the same file twice is safe.

1. Choose#

  1. On Home, press the import button — the database icon with an arrow.
  2. Choose the payer the file belongs to.
  3. Press Choose a file and pick the CSV.

The file is read right there, without sending anything to the server. While it does you will see "Reading and checking the file…". When it finishes, the card says what it found: how many trips, which broker layout, and which days it covers.

Check that before going on. It is your last chance to notice it is yesterday's file.

The check before anything is sent#

This is the part that will save you the most. Before there is anything to press, the screen has already been through the whole file, and if it finds rows that will not import, it says so in an amber box listing them: line number, patient, and what is wrong with each.

Four things are visible without asking the server:

WhatWhy it cannot be imported
No TripIdIt is the identifier an import is matched on. Without it a trip that already exists cannot be told from a new booking
Patient cannot be told apartNo rider ID and no phone. On a name alone, two patients who share one become the same record
An address missingA trip needs both a pickup and a dropoff
Address too longOver 450 characters

And a fifth that appears under another name: if the date is empty or in a format that layout does not use, the row comes out as "The line could not be read as a trip" with the exact reason under it, for example Invalid date: 13/45/2026.

The warning does not block you

You can correct those rows in the file and choose it again, or import anyway: the good ones go in and the rest wait for you in the repair list. Both are valid; the screen only makes sure the decision is yours and informed.

  1. Press Import now.

The payer you choose decides what the driver is asked for

It is not a label: it decides what will be required of the driver on every trip in the file — signatures, odometer, code scanning. The screen stops you when the file's layout does not match the payer, but between two payers that share a layout it cannot know.

2 and 3. Importing and reviewing are one screen#

Nothing jumps when it finishes. What you watch while it imports is what you are left with, with the numbers filled in.

The six figures#

A row of tiles, and they fill in as it goes:

  • new — trips that did not exist
  • updated — trips that were already there and have been refreshed
  • rejected — the ones that did not go in
  • warnings — they went in, but are worth a look (see below)
  • requests — how many calls to the server the whole thing cost
  • elapsed

Keep an eye on the request count

A file of four hundred trips is about six requests. If you ever see that number climb, tell us: it would be a regression, and an expensive one — the shared server reads a burst of requests as an attack and cuts the connection part-way through an import.

The overall progress#

Below them, one bar with the percentage and a line that reads the same before and after: "147 of 148 trips imported, 1 with problems".

That bar never goes backwards and never reaches the end twice: every request the import is going to make is declared before it starts, and the percentage is the sum of all of them.

Details#

A disclosure, collapsed to start. Opening it grows downwards without moving anything above it, and holds two things:

  • A bar per request: locating addresses, batch 1 of 2, batch 2 of 2… each with what it is carrying and what it came to ("98 new, 2 updated, 0 rejected").
  • The account of what is happening, line by line with the time: the addresses being located, every rejected row with its reason, and every wait when the server asks for calm.

A batch in flight does not say "15 of 100"

While a batch is in flight its bar sweeps without a percentage, on purpose. The server works through the hundred trips in a hundred transactions and says nothing until it has finished them all: there is no half-way figure to show you. The moment it answers, the bar fills and says exactly what happened to those hundred.

The detail stays after it finishes. It is the evidence of what the import did.

You cannot leave while it runs. A half-imported file with nobody watching is a file nobody knows the state of.

Putting right what did not go in#

If anything was rejected, Rows that need a hand appears below: a table of them and, on the right, the card for whichever one you have selected.

Pick a row and the card gives you, in this order:

  1. What is wrong, in one line.
  2. If we caught it here, a caught before sending badge.
  3. What to change: the actual instruction, not the problem restated.
  4. What the file or the server said, verbatim, when it adds something.
  5. The whole trip, filled in with its real values, and the field at fault outlined and labelled in red.
  6. Import this row.

When a row goes in it turns green and leaves the Still to fix filter.

The button stays off until the correction works

Not fussiness. If a row was rejected because the patient cannot be told apart and you change something else, sending it again only buys the same rejection. The screen waits for the field that matters.

Once you have several fixed, Import everything fixed sends them in a single request, whether that is two or forty.

When the problem is a duplicate#

This is where the screen helps most. When a trip clashes with one that already exists, the card shows you which one: its TripId, the patient, the day, the window and both addresses.

With that in front of you there are exactly two honest ways out:

  • If this row is that trip → put its TripId on the row. It stops being a booking and becomes an update.
  • If it is a different journey → change the day, the window or one of the addresses.

If it is neither, that trip should not be in the file.

Taking the rest with you#

Export what is left writes the outstanding rows to a CSV in the exact format of the file you imported: same header, same columns, same quoting. It is not a report, it is a file that can be imported again.

The name carries the payer, the date and the words not-imported, so nobody mistakes it for the good one.

Warnings, which are not rejections#

A warning is a trip that did go in but is worth a look. There is one today: the address could not be located on the map.

The trip is in the system and the day can be dispatched, but that journey cannot be routed or drawn. You find them afterwards with the missing coordinates filter on the trips list.

They are counted apart from the rejections on purpose: a warning is not a failure, and folding it into the same figure would make a good day look like a bad one.

What can go wrong#

The screen will not let you press Import. Read the red box: it says exactly what is missing. Usually the file's layout does not match the payer you chose, or the file has no rows.

"The import stopped". The server stopped answering part-way through the file. The trips that had already gone in are stored. Wait a couple of minutes and import the same whole file again.

A row says it cannot be fixed here. Some problems are ours rather than the file's, or have to be corrected in the CSV itself — a shifted column, a stray quote. The card says so and gives you a support reference: send it as it is, it is the key to the full record on the server.

Repeating an import is safe

Trips are recognised by the broker's identifier. One that already went in is updated, never duplicated. So when in doubt, import again: you will not send two vehicles.

A trip you cancelled stays cancelled even if it comes back in the file. Its details are refreshed, but it is not reinstated on its own — that would put a vehicle on a route for a journey the office had closed.

Common questions#

Can I close the screen and carry on tomorrow with what is left? No. The list of problem rows lives on the screen and goes with it, on purpose: it holds patient names, phones and addresses, and that is not kept on disk. If you have to stop, export what is left before you go.

Does importing twice duplicate anything? No. It is the recommended way out when something goes wrong.

Why are the rows that went in not shown? Because there is nothing to do with them. This screen is for what needs a hand.

I edited a row and the button is still off. The correction does not answer the problem yet. Look for the field with the red outline: that is the one to change. On a duplicate, changing just anything is not enough either — it has to be the existing trip's TripId or a different day, window or address.

What if I pick the wrong payer? If the layout does not match, the screen stops you. If it does match — two payers sharing a layout — it cannot know, and the file would go in under whichever payer you chose. That is a billing problem found a month later, so that dropdown is worth a second's attention.

How long does it take? A file of four hundred trips, a little over a minute. Almost all of that is the server storing them: each trip opens its own transaction.
