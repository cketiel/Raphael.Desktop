Import a broker's trips

How to load a broker's CSV, and how to put right the trips that do not go in without leaving the screen.

how-toNew in 1.6.1

Importing puts the trips a broker sent you in a file into the system, without typing any of them by hand.

When you need it#

The broker has sent tomorrow's CSV and those trips have to be on the Home tab before anybody starts routing.

The three steps#

The screen says so along the top: Choose → Import → Review. Nothing is imported until you ask for it.

1. Choose#

  1. On Home, press the import button — the database icon with an arrow.
  2. Choose the payer the file belongs to.
  3. Press Choose a file and pick the CSV.

The file is read right there, without sending anything, and the screen tells you what it found: how many trips, which broker layout, and which days it covers. Check that before going on — it is your last chance to notice it is yesterday's file.

  1. Press Import now.

The payer you choose decides what the driver is asked for

It is not a label: it decides what will be required of the driver on every trip in the file — signatures, odometer, code scanning. The screen stops you when the file's layout does not match the payer, but between two payers that share a layout it cannot know.

2. Import#

The bar shows the percentage and what it is doing. Below it, if you leave Show what is happening on, the detail scrolls past: addresses located in one batch, batches sent, every row that is refused and why, and every wait when the server asks for calm.

You cannot leave while it runs. A half-imported file with nobody watching is a file nobody knows the state of.

3. Review#

At the top, the figures: how many new, how many updated, how many rejected, how many warnings, how many requests it cost and how long it took.

If nothing was rejected, you are done.

Putting right what did not go in#

Whatever did not go in appears in a table below, and every row carries its problem explained and what to do about it.

Selecting a row opens its card on the right:

  • What is wrong, in one line.
  • What to change: the actual instruction.
  • The fields that fix that problem — only those, not all twenty of the trip.
  • Import this row, which lights up once the correction really answers the objection.

When a row goes in it turns green and leaves the Still to fix filter.

The retry button stays off until the correction works

Not fussiness. If a row was rejected because the patient cannot be told apart and you change a comment, sending it again only buys the same rejection. The screen waits for the field that matters.

Once you have several fixed, Import everything fixed sends them in a single request, whether that is two or forty.

When the problem is a duplicate#

This is where the screen helps most. When a trip clashes with one that already exists, the card shows you which one: its TripId, the patient, the day, the window and both addresses. With that in front of you the decision is easy:

  • If this row is that trip, put its TripId on the row. It stops being a booking and becomes an update.
  • If it is a different journey, change the day, the window or one of the addresses.
  • If it is neither, leave it out of the file.

Taking the rest with you#

Export what is left writes the outstanding rows to a CSV in the exact format of the file you imported, same header, same columns. The name carries the payer, the date and the words not-imported, so nobody mistakes it for the good one.

Correct it wherever suits you and import it exactly like the original.

Warnings, which are not rejections#

A warning is a trip that did go in but is worth a look. There is one today: the address could not be located on the map. The trip is in the system and the day can be dispatched, but that journey cannot be routed or drawn. You find them afterwards with the missing coordinates filter on the trips list.

What can go wrong#

The screen will not let you press Import. Read the red box: it says exactly what is missing. Usually the file's layout does not match the payer you chose.

"The import stopped". The server stopped answering part-way through the file. The trips that had already gone in are stored. Wait a couple of minutes and import the same whole file again.

A row says it cannot be fixed here. Some problems are ours rather than the file's, or have to be corrected in the CSV itself — a shifted column, a stray quote. The card says so and gives you a support reference: send it as it is, it is the key to the full record on the server.

Repeating an import is safe

Trips are recognised by the broker's identifier. One that already went in is updated, never duplicated. So when in doubt, import again: you will not send two vehicles.

A trip you cancelled stays cancelled even if it comes back in the file. Its details are refreshed, but it is not reinstated on its own.

Common questions#

Can I close the screen and carry on tomorrow with what is left? No. The list of problem rows lives on the screen and goes with it, on purpose: it holds patient names, phones and addresses, and that is not kept on disk. If you have to stop, export what is left before you go.

How many requests does an import cost? Very few, and the screen tells you. A file of four hundred trips is about six. If you ever see that number climb, say so: it is a regression.

Does importing twice duplicate anything? No. It is the recommended way out when something goes wrong.

Why are the rows that went in not shown? Because there is nothing to do with them. This screen is for what needs a hand.
